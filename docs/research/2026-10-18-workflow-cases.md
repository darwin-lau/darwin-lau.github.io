# Workflow 文章的案例与数据核验

核验日期：2026-10-18。只使用已阅读全文的一手公开资料；以下产品行为没有亲自实测。这里核实的是几类工作如何分工，不是 Dify、Coze、代码编排之间的横向胜负。

## 1. Vercel d0：删掉替模型思考的中间工具

来源：[Andrew Qu，We removed 80% of our agent’s tools](https://vercel.com/blog/we-removed-80-percent-of-our-agents-tools)，2025-12-22。

d0 回答 Slack 里的数据问题，将自然语言转成 SQL。旧方案预筛 schema、设计查询规划和验证等专用工具；新方案让 Claude Opus 4.5 在沙箱里直接检索 Cube 语义层文件。**业务定义没有消失：维度、指标公式、join 关系已经写在结构清晰的 YAML / Markdown / JSON 里。**

原文代码旧版列出 17 个工具；新版实际列出 `ExecuteCommand` 与 `ExecuteSQL` 两个。引言所谓“一个 bash 工具”不能理解成连数据库执行工具都删除了。

原文对 5 个代表性查询的结果：

| 原始指标 | 旧方案 | 文件系统方案 |
| --- | ---: | ---: |
| 平均执行时间 / 秒 | 274.8 | 77.4 |
| 查询成功数 | 4 / 5 | 5 / 5 |
| 平均 token，约数 | 102,000 | 61,000 |
| 平均步数，原文报告 | 12 | 7 |
| 所述最差查询耗时 / 秒 | 724 | 141 |
| 所述最差查询步数 | 100 | 19 |
| 所述最差查询 token | 145,463 | 67,483 |

制图建议：仅主画平均耗时与成功查询数，并把 **n = 5** 直接放在图中；token 可用约数旁注。

口径限制：

- 这是小样本内部基准，不是生产整体成功率，也不是通用 Agent 与 workflow 产品对照。
- 没有公开完整查询集、评分细则、重复次数或分布；不能补造置信区间。
- 4 / 5 → 5 / 5 是多完成一题，等价 20 个百分点，不能写成普遍成功率提高 20%。
- 原文称 token 降 37%，但给出的约数相除约为降 40%；保留原值，不包装精确百分比。
- “均步数 12”与“五题中最差 100 步”若同一分母会冲突，作者未解释。不要用步数作图佐证。

## 2. Ramp Policy Agent：政策可以交给模型，审批权限仍要配置

来源：[Use Policy Agent for approvals](https://support.ramp.com/use-policy-agent-for-approvals/)，官方帮助文档，页面未标发布日期，2026-10-18 读取。

它读收据 OCR、商户、交易、差旅与政策，给出批准、需复核、拒绝三类建议。复杂政策可写成自然语言，不必给每种细节单画分支；但自动批准发生在哪个金额、部门、Spend Program 范围，仍由审批 workflow 决定。不符合条件的费用继续进入后续审批或人工复核。记录包含政策版本与人工覆盖。

最直接的原文短证据：“For assessments, policy text is sufficient. For automatic outcomes, pair your policy with workflows”。同页也建议将大部分细碎政策判断移进政策文档，留下重复收据等少量确定性 flags。

可画结构图（产品行为示意，**不是实测流程轨迹**）：

```text
费用与凭证 → Agent 解释政策、提出建议 → workflow 检查自动批准条件
                                         ├─ 符合 → 自动批准
                                         └─ 不符合 / 不确定 → 后续审批或人工复核
```

限制：文档没有自动化率、错误率、节省工时等运行数据。`<$1,000` 是官方配置示例，不是统一产品阈值或观测结果。不能把建议正确等同于取得批准权限。

补充核验：[Identity](https://agents.ramp.com/docs/guides/identity)，同日读取，未标发布日期。独立 agent 身份属 limited early access；加入审批链本身不授予权限，还需管理员显式赋权。这支持权限边界判断，不能写成大规模客户部署证明。

## 3. Nooks：通话结束以后，真正烦人的可能是 CRM 失败

来源：[How Nooks scaled their AI platform 100x without breaking](https://temporal.io/resources/case-studies/nooks)，2026-04-08。Temporal 发布的客户案例，数据为客户自报，非独立对照实验。

一次通话保存触发：校验通话数据 → 转录 → 翻译 → 获取联系人元数据 → 写内部系统 → 分发外部集成。各步是独立可重试的 Activity。CRM 同步遇到限流与失败，慢任务与下一轮重叠时用 `BUFFER_ALL` 排队。这里 workflow 的意义是保存进度、重试失败步骤，不能靠让模型更会写摘要替代。

可引用原始数：

| 指标 | 文中报告 | 口径限制 |
| --- | --- | --- |
| 通话量 | 每日 30,000–40,000 → 超过 1,000,000 | 未明确时间窗；这组数本身推不出标题的 100 倍 |
| CRM 数据峰值 | 40,000,000 条 | 数据集规模，非每秒吞吐 |
| 通话流水线排障 | 需要专职工程师 → 每周约 1–2 小时 | 前值无精确工时；不可擅算节省百分比 |

限制：无公开失败率、成本或测量周期。此例主要证明 AI 产品的确定性数据流水线仍有用，不是自主 agent 决策成功案例，更不证明必须使用可视化画布。

## 可选补充：真实失败窗口，无可用精确效果数字

[Grid Dynamics 三位实施者的迁移复盘](https://temporal.io/blog/prototype-to-prod-ready-agentic-ai-grid-dynamics)，2025-09-29。一个服务于百余工厂的制造企业研究助手，原实现使用 LangGraph、Redis、Kafka。团队描述了等待人工输入后的状态不一致、过期状态、重复 agent 竞争，以及自写重试负担；迁移持久编排后删除数千行自写重试代码。此处是特定团队的旧实现问题，**不能写成 LangGraph 当前必然如此，也没有精确生产效果数据可作图。**

## 可用于正文的判断（作者观点，不冒充实验结论）

- Vercel 删除的是“先替模型规定怎么查”；Ramp 保留的是“什么时候有权批”；Nooks 保留的是“系统坏了一步之后怎么办”。三件事不能因为都画成节点就混为一谈。
- 一个贴切比喻：导航可以自己找路，不能因此拆掉收费闸机；驾驶更聪明也不能免去保存订单和支付状态。比喻只用一次，紧接实际产品行为。
- 持久编排仍有价值，不自动推出 Dify / Coze 的画布有购买价值。画布要用具体指标证明：谁能改规则、改一次花多久、出错如何回滚、运行记录能否定位、失败如何恢复。
- 不宜把三例做成统一性能排行榜。任务、评价与统计口径不同。一个小样本前后对照图，加一个明确标注示意的业务分工图，已经足够。
