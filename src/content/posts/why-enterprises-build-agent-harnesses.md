如果一家企业今天准备从零写一套通用 Agent Harness，我会先问：现成工具究竟在哪个任务上不够用？

“我们有内网”“需要权限和审计”“想换模型”，这些需求都成立。但从需要定制，到必须重写执行内核，中间还缺一份论证。

我的判断是：多数企业应该从现成 Harness 起步，把投入集中在业务接入、运行管理和任务验收上。只有当适配成本或能力边界已经成为可验证的障碍，重写内核才值得进入选项。把“企业需要自己的 Agent 系统”直接翻译成“企业需要自己写 Agent 循环”，很容易立错项目。

## 先把现成工具的能力算进账里

Harness 可以理解为让模型持续干活的那套运行机制：组织上下文、执行工具、处理工具结果、管理会话，并决定何时继续、何时停下。它不只是一个命令行界面，也不只是几行调用模型的循环。

Claude Code、Codex、Pi 的交付形态和默认取舍各不相同，不能当作三个完全可替换的黑盒。但它们已经提供了不少企业可以复用的接缝。

Anthropic 的 Agent SDK 把 Claude Code 的核心执行能力开放给应用开发者，可以接自定义工具，通过权限机制与 hooks 干预执行。[^claude] Codex App Server 面向嵌入自有产品的场景，已经覆盖认证、会话历史、审批和流式事件；管理员配置也能约束部分运行选项。[^codex] Pi 则刻意保持较小的核心，通过 extensions 和 SDK 供开发者定制和嵌入。[^pi]

这些能力当然不会自动拼成一家公司的内部平台，但足以推翻一个常见的立项前提：外面的产品只能给个人玩，企业的东西必须从头做。

给现成工具接业务 API、设置执行策略、加一个内部入口，完全可能就是正确方案。工程价值不会因为复用了内核而减少，也没必要为了显得“自研”而给这层集成换一个更大的名字。

## 业务权限不会自动从工具权限里长出来

以线上排障为例。读取日志、分析原因、提出修复建议，与实际重启生产服务，属于不同的责任范围。

运行时可以限制命令、文件和网络访问，也可以在调用前请求批准。但“当前这个人能否在这个变更窗口，对这个生产服务执行重启”，还涉及企业自己的身份、资源归属、值班关系和变更制度。这些语义不会因为模型能调用工具就自动存在。

企业需要把这些规则落实到工具接口和后端授权里。一次操作应该绑定实际操作者与任务，凭据只覆盖必要资源，关键写操作要在执行处校验。不能把一份权限很大的凭据交给 Agent，再指望系统提示词里的“请遵守规定”承担授权职责。

这里通常需要开发，但未必需要换掉 Harness。一个接好企业身份、能校验资源权限的业务工具，往往比修改规划循环更重要。现成平台能满足要求，就采购或接入；只有缺失的部分才需要自己补。

业务接口的形状也会影响结果。允许 Agent 提交一个带版本号、预检查和授权凭据的变更申请，与直接给它一把任意执行命令的钥匙，要求模型承担的判断责任完全不同。后者在开发者本地环境里可能很方便，搬到生产业务里就需要重新设计边界。

**企业对结果的责任，不能外包给模型的自觉。** 这才是需要掌握的能力，至于承载它的循环由谁编写，要另算一笔账。

## 任务离开终端以后，问题才完整

一个人在终端里使用 Agent，可以看着输出，发现跑偏就中断。无人值守的任务要回答更多问题：进程退出后任务算失败还是待恢复？用户撤销授权后，正在运行的任务怎么办？同一个操作被重新执行，会不会产生重复副作用？

这些责任分布在 Harness、宿主系统和业务服务之间。现成产品、宿主协议和工作流基础设施已经解决了其中一部分。企业要查明哪里还缺一环，把端到端责任接起来。

还有一层更容易被界面上的流畅体验掩盖：验收。

Agent 连续调用了很多工具，最后给出一段像样的解释，不等于任务成功。改代码要看测试和实际行为；排障要看证据是否支持结论；执行变更要看业务状态是否正确。日志能帮助解释它做过什么，却不能替业务定义什么叫做对。[^evals]

因此，我更愿意优先投资一套贴近真实工作的评测集。它应当包含正常任务，也包含缺资料、权限不足、工具超时、指令冲突等情况。评分不能只看答案是否漂亮，还要看错误操作、人工接管、返工和最终完成成本。

这套东西可以一直积累。今天用 Claude Code，明天换 Codex，后天把某个任务收敛成专用服务，都需要同一把尺子。反过来，如果团队没有自己的验收标准，即使掌握了全部源码，也很难证明自建版本比现成方案更好。

Anthropic 的一项长任务实验很能说明问题：首次会话负责初始化环境，后续会话逐项实现功能，通过进度记录、Git 提交和端到端测试衔接工作。文章特别注明，这两类 Agent 使用相同的 system prompt、工具和 Harness，差异在各自的初始用户提示。[^long-running] 这不是所有任务都该照搬的配方，但它说明，设计好交接和验收机制，可以在复用执行内核的基础上完成。

## 有些内核确实值得自己写

复用优先不等于“能扩展就永远不能重写”。一个框架在技术上允许扩展，不代表围绕它的适配、升级和排障成本合理。

例如，任务只有少量固定工具、严格受限的输出和清晰的停止条件。接入一个面向代码仓库、终端和长会话设计的通用 Agent，可能反而要处理许多不需要的假设。写一个小型专用循环，未必比维护适配层更贵。

另一种情况是，团队确实需要改变上下文压缩、状态保存、执行调度或工具错误恢复方式，而现有接口无法经济地表达这些要求。这里的关键是“经济地”：不必等到技术上绝对做不到，但应当能拿出持续适配的成本，以及替代方案的收益证据。

部署环境、数据处理条件和可用授权也可能形成硬约束。不过，“我们要求可控”还不够具体。需要说明到底是哪种部署方式、哪项运行行为或哪条授权条件不满足，以及现成的自托管产品、SDK 或托管配置为什么解决不了。

有必要自建时，也尽量把问题收窄。为一个明确业务写一个可测试的小运行时，与建设一套兼容所有模型、所有工具、所有任务的通用平台，是两种完全不同的投资。

后者最容易低估维护成本。第一版跑通循环不难；模型升级后是否回归、工具协议变化后如何兼容、会话恢复有没有丢失状态，才会持续消耗团队。所谓“模型无关”，也不能只用接口适配来证明，最终仍然要回到任务表现。

## 立项前，先做一次同场比较

我会要求团队先选一批有代表性的真实任务，在相同权限、工具、数据条件和预算约束下，比较现成方案、经过必要扩展的方案，以及最小自建原型。高风险动作应在可回放的测试环境里验证。

重点看每个被业务验收的任务花了多少钱、多久，需要多少人工修正，以及会发生什么不可接受的错误。把集成和维护的人力也算进去。一次演示成功，或某个公开榜单分数领先，都不能替代这轮比较。

如果主要问题是工具拿不到正确数据，就先修工具；如果是需求说不清，就先补验收；如果是任务经常中断，就检查状态和恢复链路。只有当问题确实落在执行内核里，而且自建能持续改善结果，才把预算往那里移。

是否需要统一的 Agent 平台，取决于任务和规模。即使需要，最值得积累的部分也往往是业务规则、工具契约、失败样本和验收标准。通用执行内核能复用就复用。要重写，先说清楚复用方案到底卡在哪里。
