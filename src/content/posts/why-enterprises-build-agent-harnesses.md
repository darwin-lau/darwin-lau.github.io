**企业应该建设适合自己任务的 Harness，但不该默认重写一套通用执行内核。** 我支持前一笔投入；后一笔投入，需要立项者先说清楚现成实现究竟卡在哪里。

Claude Code、Codex、Pi 已经很好用了，为什么企业还要做自己的东西？因为通用工具并不知道，一张任务单在这家公司怎样才算完成。代码改完之后必须检查什么，失败后允许再试多久，什么时候交还给人，这些决定仍要有人落实到系统里。

真正值得讨论的，是企业要改造哪些机制，而不是“买”与“自研”选一个阵营。

## Stripe 确实自建了 Harness，但没有从零开始

Stripe 的 Minions 很适合解释这个区别。它可以从讨论问题的 Slack 线程接任务，也可以从不稳定测试的工单中启动，目标是交回一份通过 CI、可供人审的 PR，中间不需要工程师一直陪跑。[^stripe-start]

Stripe 同时给工程师提供 Cursor 和 Claude Code。Minions 解决的是另一种使用方式：人把任务交出去，系统独立跑完，再把结果或问题送回来。

为此，Stripe 在 2024 年底 fork 了 Block 的 Goose，接入自己的基础设施，围绕无人值守任务继续改造。它复用了底座，也实实在在建设了自己的 Harness。[^stripe-build]

看它具体做的事，比看“自研”这个标签有用：任务拿到预热好的隔离开发环境；规则和上下文按需装配；写完代码后，lint、push 和 CI 由程序确定执行。首轮 CI 失败，可以自动修复或让 Agent 再改一次；最多两轮 CI，随后交人处理。[^stripe-build]

这些安排本来就属于 Harness 工程，不能统称为无关紧要的“外围”。它们决定了模型能不能在这个代码库里交付结果。复用 Goose，也没有让这部分工作自动消失。

这像给新同事办入职：人招到了，仓库权限、开发环境、测试命令和交付方式仍得安排。招到高手，不会成为撤掉 CI 的理由。

其中“最多两轮 CI”尤其有分量。继续尝试可能修好，也可能只是继续花钱。Stripe 把停止条件写进系统，没有把无限重试当作无人值守的标志。这个决定不需要模型更聪明，需要负责交付的人明确取舍。

这就是我赞成企业自建 Harness 的理由：公司要把自己的工作制度变成实际执行的约束，不能只把制度写进提示词，然后等 Agent 自觉遵守。

## 先把完成标准接上，再决定是否改内核

假设任务是修一个失败测试。Agent 改了代码，解释看起来也合理，系统却没有运行项目要求的测试。这时缺的是验收步骤。先把它接到执行路径里，比先换一套规划循环更直接。

现成工具已经提供 SDK、hooks 或扩展接口，能承载其中不少改造。[^runtimes] 企业把工单接进来、把验收接出去，可能就能得到需要的系统。工程价值取决于它解决了什么交付问题，没必要按自己写了多少底层代码来计分。

因此，我不会因为“要接内网”“要留审计记录”就赞成重写内核。这些要求应该先变成明确的接口、授权和记录规则，再检查现成机制能否承载。否则，一个连业务边界都没想清楚的项目，很容易先花掉最多的钱，复制通用工具已经做过的部分。

Stripe 的选择也有时间背景：它在 2024 年就开始 fork Goose。后来 SDK 和扩展能力继续发展，今天的团队应该重新检查接入成本，不能拿别人的历史选择替自己免掉这一步。

## 重写要有具体障碍，不能只有平台愿景

我会支持重写的情形很明确：业务需要的状态恢复、上下文管理或执行调度，现成接口始终无法合理表达；为了绕过这些限制，团队不断侵入式修改，每次升级都要重打补丁。此时维护一个范围更窄的运行时，可能比维护适配层便宜。

这个理由不要求证明现成工具一无是处，却要求指出具体障碍，并把新内核的回归、兼容和长期维护一起算进去。第一版跑通几天，说明不了这笔投资是否划算。

反过来，如果真正的失败是取不到工单信息、没有可靠的测试、权限语义还没定义，那么重写内核不会替团队补上这些东西。它只会让团队同时维护业务问题和底层问题。

我的建议是：先拥有任务标准、工具契约和失败记录，在现成底座上建设企业 Harness；等这些记录明确指向内核限制，再动内核。可以购买的运行能力也照样购买，不需要把每一层都变成自研项目。

如果立项材料说不清现成实现阻碍了哪一步交付，预算就不该先花在重写通用内核上。
