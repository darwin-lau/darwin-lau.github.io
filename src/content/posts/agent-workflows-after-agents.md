**对工程师维护的新 Agent 应用，我会默认使用代码和现成运行时，不会因为能拖拽节点就再引入一个平台。** Dify、Coze 要让规则变更、交付或故障处理更省事，才值得增加这一层依赖。

这是一条选型立场。业务里的审批、重试和状态管理当然还要存在，但“流程仍有必要”，不能替某个工作流产品证明购买价值。

要看哪些东西该删、哪些该留，Vercel 和 Ramp 的做法比一场“Agent 会不会淘汰 workflow”的争论更具体。

## 替模型规划探索路线的步骤，可以删

Vercel 的内部数据助手 d0 把 Slack 里的问题转成 SQL。早期方案准备了许多专用工具，替模型筛选资料、查 schema、规划查询、验证语法。后来团队删去大部分中间工具，让模型直接在沙箱里检索 Cube 语义层文件，再执行 SQL。[^vercel]

关键在于，文件里已经写清了维度、指标公式和关联关系。业务知识还在，模型只是拿回了自己找资料、决定阅读顺序的空间。

这像图书馆已经有清楚的书架和目录，却要求每位读者按一张预画的路线找书。读者已经会查目录，这张路线就可能成为负担。把书架整理好，往往比继续增加路标有用。

我会优先尝试删掉这类编排。模型已经能完成探索，就让它探索，再验收结果。没有必要把人猜测的每一步思路都固化成节点。

## 批准权不该每次重新推理

Ramp 的 Policy Agent 走了另一条很清楚的边界。它结合票据 OCR、商户、差旅资料和公司政策，给出建议批准、需要复核或建议拒绝的判断。[^ramp]

它的文档举过一条政策：电脑配件必须用指定的 IT 采购虚拟卡购买。模型可以结合票据和卡片信息理解这条规定，团队不必为每种商户叫法、描述方式和例外组合画分支。

但自动批准发生在哪些金额、部门或项目范围，仍由审批流程配置。不符合条件的申请，继续走后续审批或交给人工；记录里还会保留所用政策版本和人工覆盖决定。[^ramp]

公司规定某类申请必须人审，就应该执行这条规则。模型对申请多有信心，都不是临时扩大批准权的理由。

Vercel 让模型自己决定怎样查资料，Ramp 把批准边界保在系统里。我赞成这样的分工：把探索交还模型，把已经作出的业务决定执行到底。更强的 Agent 能减少一部分人工编排，不会替公司取消制度。

## 流程存在，不替画布产品担保

Dify 已有 Agent 节点和可暂停的人工输入节点；开源 Coze Studio 也把 Agent、工作流和发布能力放在同一平台里。[^platforms] 它们不必选边站到 Agent 的对面，但多一个 Agent 节点，也不足以成为长期价值。

真正值得买的，是团队能少维护多少东西。

继续看费用审批。财务要调整免审额度，如果能在有权限和测试的范围内修改、验证、发布，平台缩短了业务变更的链路。统一的发布、运行记录和故障定位，也可能替工程团队省下实在的工作。这些收益与谁来拖节点无关，要看整条交付过程是否更省事。

如果改同一条规则，反而得在画布、代码节点和外部服务之间逐个排错，平台就需要解释这层新增复杂度。少写几次 API 调用，不足以抵消以后持续的调试和迁移负担。

这也是我把代码作为工程团队新项目默认选项的原因：已有的版本控制、测试和审查机制可以继续用，coding agent 又能承担一部分实现工作。平台应该用它多解决的事情争取预算，不能只拿“不用写代码”作保证。

已经稳定运行在 Dify、Coze 上的业务，则没有必要为了追逐 Agent 再迁一次。保留它的理由应该是它仍在降低交付和维护负担；新增它，也应该拿出同样的理由。

所以，我不会为把几次模型调用画成方框单独买单。我愿意为业务人员能可靠地改规则、工程师能更快查清故障、团队少维护一套系统买单。工作流产品能把这些事接住，就有价值；接不住，模型越强，那层画布越难解释自己的必要性。
