如果一张流程图的主要作用，是把“理解问题、拆解步骤、选择工具、整理答案”逐项画出来，那么模型能力提升以后，这张图确实值得重新审视。过去需要手工照看的推理步骤，今天可能交给一次 Agent 运行就能完成。

但由此推导“Dify、Coze 已经没用了”，跳得太远。Agent 不会自动消除业务流程和可靠执行的需要，可这些需要，也不能替某个可视化产品证明价值。流程、运行机制、开发界面，得分别看它们解决了什么问题。

我的看法是：只负责拼接提示词和模型调用的产品，价值会受到挤压。能降低业务变更、交付和运维成本的平台，仍然有位置。但这个位置必须用实际成本证明，不能靠“企业总要审批”来保住。

## Agent 改变的是谁决定下一步

Anthropic 在《Building effective agents》里给过一个很实用的区分：workflow 通过预定代码路径编排模型和工具；agent 则由模型动态决定过程与工具使用。[^effective-agents] 分界在控制权，跟有没有画布无关。

一个全用代码写的系统，也可能是工作流。一个可视化流程里的节点，也可以运行 Agent。看到框和箭头就判断“落后”，看到模型循环就判断“先进”，没有多少工程意义。

例如，研究一个陌生代码库的问题，事先很难穷举要看哪些文件、运行哪些命令、遇到什么错误再查哪里。把每一条路径提前画出来，容易变成替模型手写探索过程。Agent 的动态规划在这里很有用。

反过来，固定的批处理、标准格式转换、条件明确的路由，并不会因为模型更聪明就突然需要动态规划。路径已经稳定，再让 Agent 每次重新想一遍，可能只增加延迟、费用和变数。

所以，该删除的是不再必要的拆解，而不是所有确定的步骤。有些步骤存在，是因为模型能力不够；另一些步骤存在，是因为业务就要求这样执行。这两类流程不能一起宣布过时。

## 有权规划，不等于有权改规则

设想一个退款处理流程。用户的描述可能含糊，证据可能散在聊天记录和订单系统里。Agent 可以读取资料、核对矛盾、追问缺失信息，再给出建议。让模型处理这部分不确定性，比把所有表达方式写成分支自然得多。

但退款额度、审批权限、重复退款检查和实际付款，不该随着模型的临场理解一起变化。某笔申请是否可以自动通过，谁能批准超额退款，审批之后金额变了是否需要重审，都需要明确规则。

这时，一个合理的实现可以让 Agent 生成带证据的处理建议，再由确定的校验、授权和执行逻辑接手。

这也不要求所有业务都套进一张大 DAG。规则可以落在普通服务、状态机或工作流引擎里。选择哪种实现，取决于任务持续多久、如何恢复，以及谁来维护。重要的是规则有明确的执行位置，而不是只写在提示词里等待模型记住。

“模型已经能理解公司制度了”，不足以取消这层设计。理解一条制度，与系统在每次执行时强制落实它，是两回事。

## 会继续对话，不等于会可靠恢复

Agent 演示很容易给人一种错觉：只要对话历史还在，任务就能接着做。

还是退款。付款接口已经成功，调用方却在收到结果之前超时。恢复运行以后，系统该重新付款，还是查询上一笔操作？如果原来等着审批的金额被修改了，之前的批准还有效吗？任务暂停几天后，恢复时该使用哪个版本的规则？

这些问题都不能靠“再问模型一次”解决。需要保存明确的状态、区分已完成与待确认的操作，并在产生外部副作用的接口上处理幂等。模型输出看起来一致，也不能证明业务操作只发生了一次。

LangGraph 的中断文档明确提醒：恢复会从被中断节点的开头重新执行，因此中断前的外部副作用需要幂等处理。[^langgraph] Temporal 的文档也说明，Activity 已经完成、但完成结果未成功上报的情况可能导致重试，需要通过幂等设计避免重复副作用。[^temporal] 即使运行系统提供了恢复机制，业务代码仍然承担一部分正确性责任。

因此，不能从“有节点重试”“支持继续运行”，就推导出端到端事务保证。更不能因为某个平台有画布，就默认它能承接所有长任务。真正需要核实的是状态保存在哪里、失败从哪一步恢复、恢复是否重放、外部系统如何识别重复请求。

## Dify、Coze 已经在吸收 Agent

把这些产品概括成“上一代固定流程”，也不符合它们现在的能力。

Dify 的工作流里已经有 Agent 节点，可以循环调用工具；人工输入节点可以暂停执行，收集响应后走不同分支。[^dify] Coze Studio 提供工作流开发与自部署能力，公开 API 也包含运行、流式执行，以及问答节点中断后的继续运行接口。[^coze]

这些事实足以说明，Agent 与 workflow 在产品中可以共存。它们不足以说明每项实现都符合某家企业的审批、隔离、持久化或审计要求。尤其是“有人点了一个按钮”，与“具备正确权限的人批准了这个版本的业务操作”，中间还需要身份和授权语义。

我不认为多一个 Agent 节点，就足以成为平台的长期优势。团队能否更快、更稳地修改和交付业务，出了问题能否查清和修复，才值得持续付费。

## 画布值不值钱，看谁在维护它

如果流程主要由业务团队维护，修改频繁但逻辑相对清楚，可视化产品可能明显缩短沟通和交付链路。前提是业务人员真的能够完成变更，并且有测试、权限、版本和发布机制托住结果。能拖动节点，不等于能安全地修改生产流程。

如果主要维护者一直是工程师，流程里塞满自定义代码，复杂变更还要在画布、代码节点和外部服务之间来回追踪，那么平台可能已经变成额外的一层系统。普通代码配合测试、审查和成熟运行基础设施，未必更贵。代码节点本身没有问题，问题是整个平台是否仍在减少工作量。

比较对象也变了。我会把工程师借助 coding agent 写出的小服务纳入选项，而不只比较“买平台”和“花几个月定制开发”。如果平台的主要卖点是省掉几次 API 调用和界面开发，就要用今天的替代方案重新算账。

还有一类场景，输入和目标经常变化，路径本来就无法预定。此时应该给 Agent 足够的探索空间，再在数据访问和外部动作上设置边界。为了让任务“看起来可控”，硬画出大量推理分支，往往只会把复杂度藏起来。

与其只演示一条成功路径，不如现场改一次需求，再制造一次工具故障和中断。谁能改、要改多久、谁能定位错误，恢复后会不会重复付款，这些差别比一张漂亮的运行图更有说服力。

这一轮往往比争论“Agent 是否会替代 workflow”更有用。平台若能减少交付和维护成本，就继续用；如果只是把几次 API 调用换成几个方框，却增加了调试、发布和迁移负担，就没必要因为已经画了很多图而继续投入。

我看好的产品，会让模型接管不值得手写的探索过程，同时让业务人员和工程师保有清楚的规则与责任。至于这些规则显示成画布还是代码，应该由维护它的人决定。

## 资料与说明

本文依据公开文档讨论架构与产品价值，未做商业版功能实测或性能排名。资料查阅于 2026 年 10 月 18 日；退款是用于分析失败路径的假想案例。Coze 的具体实现引用开源 Coze Studio，不把它与所有商业版本视为功能完全相同。

[^effective-agents]: Anthropic：[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents#what-are-agents)。原文区分预定代码路径与模型动态控制，也讨论简单方案、工作流和自主 Agent 的取舍。

[^langgraph]: LangChain：[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts#side-effects-called-before-interrupt-must-be-idempotent)。说明中断后的节点重跑、幂等要求，以及生产环境的持久化 checkpointer。

[^temporal]: Temporal：[Activity Definition: Idempotency](https://docs.temporal.io/activity-definition#idempotency)。讨论 Activity 重试产生重复副作用的风险，以及与被调用系统配合的幂等设计。

[^dify]: Dify：[Agent](https://docs.dify.ai/en/cloud/use-dify/nodes/agent)、[Human Input](https://docs.dify.ai/en/cloud/use-dify/nodes/human-input)。这些节点能力本身不构成端到端业务授权或事务保证。

[^coze]: Coze Studio：[官方仓库与自部署说明](https://github.com/coze-dev/coze-studio#quickstart)、[Workflow API](https://github.com/coze-dev/coze-studio/wiki/6.-API-Reference#execute-workflow)。API 文档还包含流式执行及继续运行，不能据此推断所有外部操作都只执行一次。
